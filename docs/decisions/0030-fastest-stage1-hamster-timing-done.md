## 選択肢

### A: 3.45 時間をそのまま使い、残りの2本を待つ（推奨）

- **GPU時間**: 追加 0。
- **分かること**: 2段階学習（stage 1 + stage 2）と full AT の Hamster での時間の比。3本とも「隣の GPU にもう1本」という同じ条件で測るので、
  比は公平です。絶対値は「2本同時に回す」という実際の使い方での値になります。
- **事前に決めるルール**: 2段階学習の時間 = この stage 1 の 3.45 時間 + stage 2 の開始から終了までの時間。
  full AT の時間 = その run の開始から終了までの時間。比が 0.9〜1.1 の範囲なら「時間は同等」とし、それより外なら速い方を「速い」と書く。
  この比は時間の記述であり、2段階学習の採否は、すでに事前登録した汎化チェックのルール（MobileNetV4-M と EfficientNet-B0 の両方が基準の −1pt 以内）で決める。
- **リスク**: 「同居なし」の定義と少しずれます。epoch 24〜27 の遅れの原因が full AT 側の何か（検証の時間帯など）だと、両方の計測に同じように入ります。

### B: A に加えて、ホストを空けて stage 1 を測り直す

- **GPU時間**: 約 3.3〜3.6 時間。full AT の計測が終わるまで（約 12〜13 時間後）始められません。
- **分かること**: 人間が決めた指標どおり「cuda_graph・同居なし」の stage 1 の時間。A の値との差で、同居による遅れの大きさ。
- **事前に決めるルール**: 測り直した時間が 3.45 時間と 5% 以上違えば、コストの表には測り直した値を使い、full AT と stage 2 も同じ条件で測り直すかを別の packet で決める。
  5% 未満なら 3.45 時間を使う。精度は Ferret 版・今回と一致することを確認するだけで、判定には使わない。
- **リスク**: 結果は精度に何も足しません。full AT と stage 2 も同居で測っているので、stage 1 だけ測り直すと条件がそろわなくなります。
  公平にするには、結局3本とも測り直す必要が出て、合計 20〜30 GPU時間になりえます。

## 推奨

A を推奨します。いま走っている2本（full AT と stage 2）は、どちらも隣の GPU にもう1本ある状態で測られるので、
3本をこの同じ条件で比べるのが一番そろった比較です。B で stage 1 だけ測り直すと、かえって条件がずれます。
また、epoch 24〜27 の遅れを除いても変わるのは約 0.1 時間（約 3%）で、上の「10% 未満の差は読まない」という目安より小さいです。
次のどれかが起きたら判断を変えます。(1) full AT と2段階学習の時間の比が 0.9〜1.1 の境目に来て、どちらとも言えないとき。
このときは、3本とも同居なしで測り直す新しい plan を書くのが筋です。(2) 論文で絶対的な GPU 時間を報告することになったとき。
(3) full AT の run でも同じような原因不明の遅い区間が大きく出たとき。
