## 選択肢

### A: 原因を CPU だけで調べる（おすすめ）

- **GPU時間**: 0（CPU で 1〜2 時間の作業。`CUDA_VISIBLE_DEVICES=""`、ピン留めした worktree `source-5dd329eaf31f` で行う）。
- **やること**: ConvStem 版・深く細い版・標準の Atto を seed 0 で作り、次の3つを比べます。
  (1) 初期状態で、画像ごとに出力がどれだけばらつくか。
  (2) 同じ 8 枚に、プロジェクトの optimizer の設定で AdamW を 200 step かけて、損失が下がるか（覚えられるか）。
  (3) この run の `last.pt` で、stem の重みの大きさと、プーリング後の特徴の画像ごとのばらつき。
- **わかること**: 原因が「モデルと optimizer の側」か「GPU の側」か。
- **事前ルール**: ConvStem 版だけが 8 枚を覚えられない（200 step 後の損失が ln(1000) − 1 より下がらず、ほかの2つは下がる）→ モデル側の問題。原因を直す計画を書き、「学習が止まっていないこと」の回帰テストを付けて、科学レビューのあと再実行を別の packet で決める。
  3つとも覚えられる → CPU では再現しない。GPU の側（仮説 b）が有力として、GPU での短い確認を別の packet で決める。
  ConvStem 版の出力が初期状態から一定（画像ごとのばらつきがほぼ 0）→ 仮説 a。上流の初期化と比べてから、直し方を計画に書く。
- **リスク**: CPU で再現しないこともあります。その場合でも、原因の候補を半分に絞れます。

### B: ConvStem の問いを閉じる

- **GPU時間**: 0。
- **わかること**: 新しいことはありません。「ConvStem は Phase 2 で有効な結果が出ず、試せなかった」と記録し、batch B は深く細い版の結果だけで終えます。
- **事前ルール**: 論文の表に ConvStem の行は載せません。あとで ConvStem を問う場合は、新しい計画と packet で始めます。
- **リスク**: 原因がわからないままなので、ほかのモデルの変更でも同じ「完了したのに学習していない」が気づかれずに起きる可能性が残ります。ConvStem は Singh らが頑健性に効くと報告している部品で、文献との比較の点では閉じるのは惜しい行です。

### C: 同じ設定でもう一度回し、epoch 0 で確かめる

- **GPU時間**: epoch 0 だけで約 0.6 時間（この run は 1 epoch 約 2,030 秒、Hamster の 4090 1枚）。最後まで行けば約 29 時間。
- **やり方**: `imagenet_convnext_atto_convstem_pgd_at_phase2_adamw_random_lr1em3.yaml` をそのまま、seed 0、`5dd329e` の worktree から、新しい run id で回します。
- **わかること**: GPU の非決定的な計算のせいで偶然止まったのか、毎回止まるのか。
- **事前ルール**: epoch 0 のサブセット clean が 1.0% 以下 → その場で止め、「毎回止まる」として A に戻る。1.0% を越える → 50 epoch まで回し、基準＋EMA（59.69 / 36.92）との差に Phase 2 のルール（1.5pt 以上「効果あり」、0.5〜1.5pt「保留」、0.5pt 未満「効果なし」）を当てる。
- **リスク**: seed も初期化も同じなので、非決定的な計算の差だけで結果が変わる見込みは低いと考えます。最後まで行った場合も「なぜ前回止まったか」はわからないままで、その結果は信用しにくいです。

## おすすめ: A

止まり方は「epoch 0 から、入力によらず一定の出力」という、はっきりした形です。こういう失敗は、原因がわからないまま回し直しても同じことが起きやすく、C の 29 時間は見合いません。
A は GPU を使わず、ほかの run（蒸留の検証など）の邪魔をしません。結果で「直して回す」か「GPU 側を調べる」かがはっきりします。
B で閉じると、同じ形の失敗がほかの版でも起きうるという問題が残ります。

**判断が変わる場合**:
- ConvStem を論文に入れる予定がなく、batch B を早く閉じたい場合 → B。
- GPU がしばらく空いていて、とにかく速く一度確かめたい場合 → C（epoch 0 で止まれば 0.6 時間で済みます）。

**この packet とは別の、仕組みの問題**: 今回、走っている途中で「当てずっぽうのまま」を止める見張りがありませんでした。「epoch 0（または 1）が終わっても精度が当てずっぽうのままなら止める」見張りを足すかどうかは、学習コードの変更なので、別の計画として決めてください（CLAUDE.md のルール 3 にそって、インフラの不具合は別の計画にします）。
