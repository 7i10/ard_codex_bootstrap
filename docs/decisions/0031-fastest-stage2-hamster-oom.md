# 0031: 最速構成の stage 2（Hamster）が GPU メモリ不足で失敗

0030 の推奨 A は「full AT の計測と、この stage 2 の完走を待って、3本の時間で比べる」でした。
その stage 2 が途中で落ちたので、どう埋めるかを決める packet です。精度の判定には関係しません。

## 何が起きたか

記録: `docs/plans/0103-lightweight-imagenet-architecture-survey.md` の Progress log、
2026-10-03 (postrun, fastest-config stage 2 failed)。この run は失敗したので、record や証拠台帳の行はありません。

- run: `plan0103-mnv4s-twostage-stage2-224-cg-from50s256-hamster-s0-v1`。pinned worktree `source-65369a36668b`、
  設定 `imagenet_mobilenetv4_twostage_stage2_224_pgd3_ft_cg.yaml`、
  初期値は Hamster の stage 1 の `last.pt`（sha256 `d4e1d8fe...`）。2026-10-02 19:43:02 UTC 開始。
- watcher の判定: 終了済み、失敗、失敗の種類は `unknown`。manifest の状態は `failed` で、`completion.json` はありません。
- **原因は GPU メモリ不足です。** epoch 1 の検証が終わった直後（20:26:24 UTC）、epoch 2 の最初の攻撃の計算で
  `CUDA out of memory` が出ました。そのとき GPU の空きは 32 MiB だけで、この run が 3.64 GiB、
  **別のプロセス（PID 2384146）が 19.80 GiB** を使っていました。
- この run だけなら、ピークでも 8.7 GB なので 24 GB の GPU に十分収まります。つまり、学習のコードや設定の問題ではなく、
  外から来たプロセスが原因です。
- PID 2384146 は、いまの GPU のプロセス一覧にはいません。誰の何だったかは分かっていません。
  隣の GPU（物理 GPU 0）で動いている full AT の計測（PID 2201374）とは別物で、full AT はいまも動いています。
- 落ちた場所の理由: cuda_graph は epoch ごとにグラフを取り直すので、epoch の切れ目で新しくメモリを確保します。
  検証の間に別のプロセスがメモリを取ると、そこで落ちます。

## 2 epoch 分で分かったこと

数字は内部検証（224 px、PGD-10）で、公式テストではありません。

| epoch | val clean | val PGD-10 | 学習時間 |
|---|---:|---:|---:|
| 0 | 50.12% | 27.49% | 1,165 秒 |
| 1 | 49.48% | 27.09% | 1,156 秒 |

- 開始から epoch 1 の終わりまで 2,596 秒、1 epoch あたり約 21.6 分です。
  20 epoch に伸ばすと約 7.2 時間になります（eager のときは約 7.9 時間）。ただしこれは2 epoch からの外挿で、測った値ではありません。
- `best.pt` と `last.pt`（どちらも epoch 1）は残っています。

## ノイズの目安

- 時間について: 0030 の stage 1 では、1 epoch あたりの速度が ±3% ほど揺れ、原因不明の遅い区間もありました。
  2 epoch からの外挿は、この揺れや遅い区間を拾えません。0030 で決めた「10% 未満の差は読まない」という目安に照らすと、
  外挿の誤差はたぶん 10% 未満ですが、確かめられません。
- 精度について: この packet では判定しません。

## 選択肢

### A: 最初からやり直す（推奨）

- **GPU時間**: 約 7.2 時間（Hamster の GPU 1。full AT の計測と同居、0030 と同じ条件）。
- **分かること**: 0030 で決めたとおりの「stage 2 の開始から終了まで」の時間。full AT・stage 1 と同じ条件で、3本の時間がそろいます。
- **事前に決めるルール**: 0030 A のルールをそのまま使います（2段階学習の時間 = stage 1 の 3.45 時間 + この stage 2 の時間、
  full AT との比が 0.9〜1.1 なら「同等」）。決定的モードなので、epoch 0 と 1 の val が上の表と一致することも確認します
  （一致しなければ、時間の比較の前にその理由を調べます）。
- **起動コマンド**: plan の Progress log に書きました。新しい run id（`-s0-v2`）と新しい出力先を使い、v1 の出力は消しません。
- **リスク**: 同じ外部プロセスがまた来ると、また落ちます。起動前に `nvidia-smi` で GPU が空いていることを確認する以外に、こちらで防ぐ方法はありません。
  full AT の計測は残り約 12 時間なので、この run（約 7.2 時間）は full AT より先に終わる見込みです。

### B: epoch 1 から再開する

- **GPU時間**: 約 6.5 時間（A より約 0.7 時間少ない）。
- **分かること**: A と同じ精度。時間は「1本目の 2 epoch + 再開後の 18 epoch」をつなぎ合わせたものになります。
- **事前に決めるルール**: A と同じ。時間は2つのプロセスの開始〜終了の合計とし、間の止まっていた時間は数えない。
- **リスク**: 起動の時間を2回数えます。run-bundle が「失敗した区間 + 再開した区間」の2つになり、記録が複雑になります。
  節約できるのは 0.7 時間だけなので、記録の分かりやすさと比べると割に合いません。

### C: やり直さず、見積もりを使う

- **GPU時間**: 追加 0。
- **分かること**: stage 2 の時間の目安（約 7.2 時間）だけ。0030 で決めた「測った時間」にはなりません。
- **事前に決めるルール**: 2段階学習の時間 = 3.45 時間 + 7.2 時間 ≒ 10.7 時間として full AT と比べる。比が 0.8〜1.2 の範囲に入ったら
  「どちらとも言えない」とし、A をやる。
- **リスク**: 外挿なので、遅い区間や epoch ごとの保存・パネル出力の時間を拾えません。2段階学習の精度はすでに Ferret の run で分かっていますが、
  この Hamster 版の stage 2 を完走させないと「最速構成での時間と精度を同じ run で測った」とは言えなくなります。

## 推奨

A を推奨します。失敗の原因は外のプロセスで、設定もコードも変える必要がありません。同じものをもう一度回せば、0030 で決めた比べ方がそのまま使えます。
B は節約が 0.7 時間しかなく、記録が2つに割れます。C は GPU を使いませんが、0030 で決めた「測った時間」という定義を変えることになります。
次のどれかがあれば判断を変えます。(1) PID 2384146 が誰かの長く続くジョブだと分かり、Hamster の GPU 1 がしばらく空かないとき。
このときは、full AT の計測が終わるのを待って GPU 0 で回すか、C に切り替えます。(2) full AT の計測も同じ理由で落ちたとき。
このときは、3本とも測り直す新しい plan が必要です。
