## この packet が扱っていること

plan 0096 は 24 本の arm を訓練し、そのうち 12 本が終わった。**そして endpoint
評価はまだ一本も走っていない。** この plan の判定基準は held-out の CE-PGD20 で
あって、いま手元にあるのは各 run が自分の checkpoint を選ぶために使った検証
split の精度だけである。つまり **28 GPU 時間ぶんの計算が、読まれないまま置かれ
ている。**

問いは「どちらの割り当てが勝ったか」ではない。まだ何も判定できない。問いは
**次に何を回せば、この plan が答えを出せる状態になるか** である。

これは contrast ではないし、endpoint でもないし、結果でもない。ただし
**この plan が測ろうとしている差は、この plan の暫定閾値 0.25 pp と同じか

ということは示している。それが下の判断の中心にある。

### 床が測られていない

plan 0096 の事前登録はこう書いている。閾値は plan 0093 の 12 本の control から
出す、出ていなければ 0.25 pp を使う、と。**plan 0093 は未着手のままである**
（`docs/plans/0093-pm-online-primary-confirmation.md`「Current milestone: 事前宣言。
未着手」）。したがって 0.25 pp は測定値ではなく、仮に置いた数字である。

参考になる既知の値は範囲が広い。独立な run どうしなら e114 の held-out 精度は
RNG だけで 1–2 pp 動く。この plan の fork は e100 まで bit 単位で同一なので
対応差の床はそれよりずっと小さいはずだが、**「ずっと小さい」がどれくらいかは
誰も測っていない**。過去に記録されている control 対 control の振れ幅は軌道の
途中で 0.16–1.88 pp である。0.25 pp はその範囲の内側に落ちている。

**どの選択肢についても言えること**: 期待される効果が 0.25 pp 前後なら、床を
測るまでそれが床を越えるかどうかは言えない。3 親でも 6 親でも同じである。
親を増やすと対応差の平均の精度は上がるが、1 本の対応差そのものの床は変わらない。

## 選択肢

`alloc-v1-p6-all-fork` は 2026-09-07T23:56Z に終わり、**Hamster と Ferret の
5 枚すべてが空いている**。実行を止めている条件は `chosen` が null であること

コストの見積もりはこの campaign の実測から出している。p5 の 4 arm は 100 epoch を

- **事前規則**: 変更なし。e199 の親ごと対応差、閾値 0.25 pp、clean 精度が 0.5 pp を

- **リスク**: 床が未測定のまま 29–34 GPU-h を使う。結果が 0.25 pp を跨いだとき、

- **決まること**: この設計・この horizon・この endpoint での対応差の雑音床。

- **事前規則**: 3 つの `RANDOM(rep1) − RANDOM(rep2)` の絶対値をとり、その最大値を

- **リスク**: n=3 は粗い。床が 0.1 pp なのか 0.3 pp なのかの区別はつくが、

- **事前規則**: この中間値では何も判定しない。6 親の検定は事前登録どおり別に

- **リスク**: 大きい。結果を見てから設計や停止を決めることになり、

## 推奨とその理由

**B を先に、そのあと A。**

plan 0096 自身が「閾値は測った床から決める、なければ 0.25 pp を暫定で使う」と
書いており、その床を出すはずだった plan 0093 は未着手のままである。つまり
いまの 0.25 pp は、この plan が本来やるつもりだった手続きの穴埋めである。
B はその穴を 7–8 GPU-h で埋める。A の 4 分の 1 のコストで、**A に意味があるか
どうかを先に決められる**。

**p6 が終わったことで、この推奨は前より強くなった。** 当初この packet は
「3 本の幅が 0.1 pp しかないので、効果は閾値と同じか小さいかもしれない」と
書いていた。p6 の 3 本は 0.64 pp 開いている。つまり **効果が小さいかもしれない
という懸念に、散らばりが大きいかもしれないという懸念が加わった。** 前者だけなら
親を増やして精度を上げる道もあったが、後者は親を増やしても消えない。
0.64 pp が処置の効果なのか fork の雑音なのかは、処置が同じ 2 本を比べる以外に
決めようがなく、それを 7–8 GPU-h で決めるのが B である。

しかも B は新しい科学的契約ではない。親あたり 2 replicate は plan 0096 の Design
に元から書いてあり、実行がそこだけ 1 本になっている。B はその欠けている半分を
埋める作業でもある。epsilon も steps も step size も random start も
normalization も temperature も schedule も checkpoint の選び方も evaluation
attack も、一つも触らない。

C を推さないのは、コストではなく順序の問題である。C を先に回すと、そのあとの
すべての判断が「中間値を見たあとの判断」になる。B は逆で、処置ゼロの arm しか
見ないので、閾値を先に固定してから結果に進める。

「何もしない」を正式な選択肢に入れなかったのは、それに事前規則が書けないから
である。ただし現実の選択肢ではある — 修論の時間配分として、この問いより
先に進めたいものがあるなら、11 arm を読まないまま置くという判断はありうる。
その場合でも B の 7–8 GPU-h だけは推したい。床が分かっていれば、あとで
戻ってきたときに残り 12 arm を回す価値があるかどうかを、その場で判断できる。

**推奨が変わる条件**: (1) この設計の対応差の床がすでにどこかで測られていると
分かれば、B は不要で A に直行する。(2) 締切の都合で 12 arm を今夜から流す必要が
あるなら、B と A を並行に走らせてもよい（Ferret 3 枚で B、Hamster 2 枚で A の
先頭 2 本）。閾値を A の結果より先に固定するという条件は、それでも保たれる。
(3) 親あたり 2 replicate が意図的に 1 本に縮小されたのだと人間が確認するなら、
B は「設計の補完」ではなく「新しい control arm の追加」になる。科学的には同じ
ことをするが、plan の書き換えが必要になる。

## 2026-09-08 の書き直し — 何が変わったか

**この packet を最初に書いた時点では p2/p3/p4 が未着手で、選択肢 A は 12 本の訓練
（28–31 GPU 時間）を含んでいた。それは終わった。** 6 親 × 4 arm の 24 本すべてが
epoch 199 に到達し、GPU は全部空いている。A の費用は endpoint 評価だけになり、
約 4–6 GPU 時間に下がった。

同時に、**B を先に置く理由は弱まっていない。むしろ強まった。**

選択 split（判定指標ではない）で読んだ 3 つの対比は、いずれも 0.25 pp の暫定閾値の
内側にある。

| 対比 | 平均 | SD | SE |
| --- | ---: | ---: | ---: |
| `SAFE − RANDOM`（主要） | +0.050 pp | 0.275 | 0.112 |
| `FRAGILE − RANDOM`（副次） | −0.117 pp | 0.290 | 0.119 |
| `SAFE − FRAGILE`（方向） | +0.167 pp | 0.302 | 0.123 |

**効果が閾値の内側にあるときこそ、閾値が正しいかどうかが結論を決める。** 効果が
1 pp あれば床の推定が 0.2 pp ずれても結論は動かないが、効果が 0.17 pp のときは動く。
床を測らずに「すべて閾値内」と宣言すると、それは「効果が無い」ではなく「暫定閾値で
測れなかった」の言い換えにしかならない。plan 0096 自身が第 4 の事前登録分岐として
「三つとも互いに閾値の内側 = 両方向の per-sample 割り当てを同時に閉じる」を
**結果として報告する**と定めている以上、その閾値は測られている必要がある。

なお 6 親から得た SD 0.275 / 0.290 / 0.302 pp は、**床の上界であって床ではない。**
親ごとの真の異質性と run 雑音が混ざっている。B はその二つを分ける。

## 順序についての注意

A を先に走らせて結果を見てから B で閾値を決めることは、事前登録の破棄にあたる。
**B（または C）を先に確定させるか、A を先に走らせて閾値は 0.25 pp のまま動かさないか、
どちらかである。** 中間はない。

A を選ぶ場合、この packet はそれを記録し、報告には「閾値は測られた床ではなく事前
登録された暫定値である」と明記する。


## 決定（2026-09-08、本人）

**B を選択。** 先に床を測り、閾値を確定してから endpoint 判定に行く。
6 親、約 14–16 GPU 時間（訓練）＋ endpoint。

### 「random 対 random」が何を指すか — 実装前に確定させる

option B の文言は二通りに読める。**この plan の問いに対して正しいのは (ii) である。**

- **(i) 同じ mask、別の `continuation_seed`。** attack と大域 RNG だけを引き直し、
  データ順と拡張は固定される。これは **RNG replicate の床**であって、
  判定対象の対比の床ではない。判定される 4 arm は全部 `continuation_seed: null` で
  同じ流れを共有しており、互いの違いは mask だけだからである。
- **(ii) 同じ大きさ・同じクラス比の、別の無作為抽出。`continuation_seed` は据え置き。**
  用量とクラス比を固定したまま、**選ばれた集合の恣意的な同一性だけ**を動かす。
  これが `ALLOC_SAFE − ALLOC_RANDOM` の帰無分布そのものである。

**(i) を使うと床が過大になり、閾値が甘くなる。** そして plan 0096 の第 4 分岐は
「三つとも閾値の内側 = 割り当てを両方向で閉じる」という**無効果の主張**なので、
甘い閾値はその主張を不当に通しやすくする。保守側に外れるのではなく、逆側に外れる。
だから (ii) を採る。

`scripts/build_stagewise_allocation_masks.py` は無作為抽出を
`f"{random_seed}:{seed_label}:{class_id}:{sid}"` で鍵付けしているので、`random_seed` を
変えれば、クラスごとの員数を保ったまま独立な抽出が得られる。

### 事前規則（結果を読む前にここで確定する）

1. 6 親それぞれについて、既存の `ALLOC_RANDOM` mask とは別の `random_seed` で
   2 本目の無作為 mask を作る。員数とクラス比は既存 mask と一致すること。
   一致しなければ着手しない。
2. 各親を e100 から fork し、2 本目の mask で e199 まで訓練する。
   `continuation_seed` は既存 arm と同じ（`null`）に据え置く。
3. 6 つの `RANDOM_A − RANDOM_B` 対応差を e199 の endpoint で取り、
   **その絶対値の最大**を床とする。
4. **閾値 = max(床, 0.25 pp)。** この値を確定し記録してから、24 arm の endpoint を
   走らせて事前登録した検定を実行する。
5. 床が 0.25 pp を下回った場合も閾値は 0.25 pp に据え置く（事前登録した下限を
   結果の側から緩めない）。床が上回った場合は床を採る。

なお本 packet の主要判定は plan 0095（cohort placebo）が測ろうとしていたものと
同じ量である。監査は 0095 の control が placebo と異なる `continuation_seed` に
乗っており、測ろうとしている統計量を汚染していると指摘した。ここで (ii) を採ることは
その指摘への回答でもある。
